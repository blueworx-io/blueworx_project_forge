# Leads Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A Leads page under Clients for businesses we are talking to, moving Lead → Opportunity → Client, or into an Archive, never appearing anywhere a client does.

**Architecture:** A lead is a row in the clients table with a status of `lead`, `opportunity` or `lead-archived`. `Clients::all()` stops returning those statuses, so every existing list and picker excludes leads without being touched; a new `Clients::leads()` and a `LeadsController` (`/leads`) are the only way to read or move them. "Make client" sets the status to `active` with All staff on, so the row simply becomes a client. The Leads screen is a slimmer copy of the Clients screen, reusing its contact form.

**Tech Stack:** PHP (WordPress REST, own tables), React + TypeScript, Playwright.

**Spec:** GitHub issue #492. Decisions taken from its suggestions: contacts yes, staff no, meetings no. Onboarding is per site and a lead has no site, so it starts when the new client's first site is added, as today.

## Global Constraints

- Version bumped (minor) and changelog updated in the same PR.
- Rules page (`src/rules.ts`) describes leads.
- Leads are administrator-only, like client configuration.
- No lead or opportunity in any client list, picker, work, support, meetings, onboarding, people, standup, sales or sync health.

## Review Focus

- A lead id sent to a client route (`PATCH /clients/{id}`, memberships, sites): refused or harmless, never promoted by accident — `Clients::all()` change covers lists; `/clients/{id}` still answers but the Leads controller is the only writer of lead statuses. Test: `GET /clients?status=all` never includes a lead.
- A client (active) id sent to `/leads/{id}`: refused with 404, so the leads routes cannot archive a real client.
- A non-administrator opening Leads: denied screen, routes refuse.
- Converting an archived lead: refused; only an opportunity converts.
- The studio's own client never becomes a lead: statuses only move through `/leads`, which refuses ids that are not leads.

### Task 2: REST — `/leads`

**Files:**
- Create: `includes/Rest/LeadsController.php`
- Modify: `includes/Rest/Server.php:87` (register)

**Interfaces:**
- `GET /leads?archived=0|1` → `{ ok, leads: [ClientRecord + contact] }`
- `POST /leads` body like `/clients` (display_name, legal_name, timezone, email_domains) → `{ ok, lead }`; status forced to `lead`, staff_all false.
- `PATCH /leads/{id}` body: any of the fields above plus `status` in `lead | opportunity | lead-archived`; needs `record_version` → `{ ok, lead }`. 404 when the id is not a lead.
- `POST /leads/{id}/convert` body `{ record_version }` → `{ ok, client }`; only from `opportunity` (409 otherwise); sets status `active`, staff_all true.

- [ ] **Step 1:** Write the controller, mirroring `ClientsController::update()` for versioning and `Validate::client()` for fields (status validated separately against `Clients::LEAD_STATUSES`). Permission `Permissions::manage`, scope `Boundary::SCOPE_OPEN` with a reason ("A lead is nobody's tenant yet.").
- [ ] **Step 2:** Register in `Server.php`. `vendor/bin/phpcs` passes.
